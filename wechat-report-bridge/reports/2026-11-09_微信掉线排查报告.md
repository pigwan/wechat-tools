## 三、证据链

### 3.1 桥接侧：账号对象链被清空，框架按设计等待登录

`native/text_service.py:315-323` 的 `_check_account()` 每秒校验当前账号，读不到账号或账号不等于绑定的 `self_wxid` 就抛错并停止接收服务：

```python
account = self._read_account()
if not account or account != self.self_wxid:
    error = RuntimeError("微信已退出登录或当前账号发生变化，重新连接并自动识别")
    self.last_error = error
    self._stop.set()
    raise error
```

`wxbot_framework/account.py:30-48` 的 `select_account_process()` 在找不到绑定账号时抛出 `等待绑定的机器人账号登录`。**这是框架的预期行为，不是 bug**——它明确要求人工完成登录后才能继续。

### 3.2 微信进程没死，只是被踢回登录界面

- 主进程 `Weixin.exe` PID **8024**，启动时间 `2026-11-08 11:52:34`，掉线时和 15:57 恢复时都是它，**从未重启**。
- 15:56:53~15:57:04 密集出现 5 个新 `Weixin`/`WeChatAppEx` 子进程，正是「重新登录」时客户端拉起登录/小程序组件的典型特征。
- 用户看到的客户端提示「为了您的账号安全，请重新登陆」是**微信服务端主动使会话失效**的标准文案；随后人工重新登录，桥接在 1 秒内自动恢复，因果链闭合。

## 四、根因判定与上游诱因

**直接根因**：微信服务端对 PC 端会话做安全校验后强制失效 → 客户端回到未登录状态 → 桥接读不到绑定账号 → 停止采集并等待登录。

**上游诱因（按可能性排序，需验证）**

1. **PC 端长期挂机 + 第三方内存读取/注入式桥接被风控识别**。该方案依赖硬编码 RVA 读取 `Weixin.dll` 内存并挂载原生接收服务，行为特征明显；「为了您的账号安全」正是风控要求重新验证的典型文案。连续三天凌晨触发，符合服务端周期性票据校验窗口。
2. **手机端会话变化**：手机微信下线、在「登录设备管理」里退出电脑登录、修改密码、或在其他设备登录同一账号，都会让 PC 端票据失效。
3. **出口公网 IP 变化**：宽带 PPPoE 定时重拨、光猫/路由器夜间重启、代理切换。本机 frp 心跳未断**不能完全排除**这一项，因为重拨发生在光猫侧且 frp 会自动重连。
4. **微信服务端夜间会话票据轮换**：长连接票据到期后要求重新登录。

> 三次掉线前都有一段业务静默期（11-07 约 51 分钟、11-08 约 35 分钟、11-09 约 2h53m 无消息），这解释了为什么「凌晨无人操作」时最容易被校验，但不是根因本身。

## 六、修复建议（按优先级）

### P0 · 今天就能做（不改代码）

1. 手机微信检查：**我 → 设置 → 账号与安全 → 登录设备管理**，删除陌生设备；确认「微信团队」通知里是否有 03:30 前后的下线/异地登录提醒；近期不要在其他设备登录同一账号、不要改密码。
2. 确认宽带/光猫是否设置了凌晨定时重拨或自动重启（在光猫管理页看「连接时长」是否与 03:30 对齐）。
3. 把「重新登录」这一步缩短到 5 分钟内：掉线后由管理台直接调 `/api/wechat-login/start` 取二维码，手机扫码即可，不必守在电脑前。
4. 在手机侧记下一次掉线时间与通知内容，用来最终确认是服务端风控还是 IP 变化。

### P1 · 本周改造（dev 环境先验证）

1. **修正守护诊断**：探测失败时区分两种状态——
   - `awaiting_login`：微信主窗口存在、账号对象链为空、且能提取到登录二维码 → **需要人工扫码**，停止无效唤醒（最多 1 次），立即告警；
   - `memory_trim`：账号对象链偶发读失败但登录态仍在 → 保留原唤醒逻辑。
   把 `reason` 写进 `wechat_health.json`，管理台直接展示原因。
2. **接上告警**：离线持续 > 5 分钟时推送一次（邮件 / Webhook / 管理台横幅），**不要依赖微信通道**（此时微信本身就不可用），恢复时再推一条。建议走已连接的邮件能力或管理台 HTTPS 页面。
3. **管理台加「重新登录」入口**：在 `admin/app.py` 的健康检查处加醒目横幅 + 按钮，点击后调二维码接口，扫码完成即自动恢复，不需要重启任何服务。
4. **降级日志**：等待登录的 WARNING 改为每 5 分钟一条 + 计数，避免日志膨胀。
5. **数据缺口标注**：断线恢复后，以 `offline_since → 恢复时间` 为窗口在日报/同步状态里标记「数据不完整」；如本地 `messages.sqlite3` 有可补数据再做补采。

### P2 · 降低复现频率（prod 长期）

1. 把守护探测间隔从 60s 放宽到 300s，减少高频内存读取这一异常特征；**同时只保留一个守护实例**（当前 `guard_pid=780`，4GB 内存机器不宜多开）。
2. 若确认是出口 IP 变化，调整光猫重拨时间窗、使用固定公网 IP 或稳定代理出口。
3. 承认「微信 PC 端会话无法 7×24 稳定」这一约束：把系统 SLA 定义为「每日人工确认登录一次」，并加一条每天 08:00 检查 `wechat_health.json` 的巡检（可用定时任务/自动化）。
4. 接受现实：微信重新登录必须手机确认，**不存在合规的无人值守自动登录方案**。目标应是把 MTTR 从 12 小时压到 5 分钟，而不是消除重登。

## 八、风险提示

- **合规与账号安全（最重要）**：本方案通过读取/注入微信客户端内存实现消息采集，属第三方非官方接入。强制下线只是最轻的后果，频繁触发可能导致账号功能受限。**不要尝试绕过微信登录/安全校验**（自动扫码、伪造票据、多开、协议号等），那会显著放大风险；也不要为了「不掉线」而提高重登频率。
- **凭据泄露**：`config.local.json` 内含 `BRIDGE_TOKEN`，`admin/auth.local.json` 内含管理台口令，两者都已在 `.gitignore` 中；报告/日志/邮件里不要出现明文。二维码接口若经公网暴露，必须 HTTPS + 强口令 + 限制有效期（`wechat_login.py` 现有 `_TTL = 300` 秒，保持）。
- **数据完整性**：断线窗口内的消息可能永久缺失，报表必须显式标注缺口，不能默认连续。
- **内存**：本机 4GB，新增常驻进程会加重换页，可能反过来触发守护原本担心的内存问题。
- **结论边界**：本报告基于本地日志、进程状态和系统事件，**无法读取微信服务端判定依据**；上游诱因（第 1~4 项）需手机侧通知或光猫日志最终确认。

## 九、常见坑

- `SetForegroundWindow` 受 Windows 前台锁限制，唤醒可能静默失败；在「真实下线」场景它本来就无效，还会抢用户焦点。
- 重新登录后 **PID 可能不变**（本次 8024 就没变），不要用 PID 变化判断「微信是否重启过」。
- `frpc.log` 为 0 字节是正常的（frp 无错误不写日志），不要据此判断穿透挂了；判断是否存活看进程和端口。
- `bot.log` 的 `RuntimeError` 计数里 2912 条是「等待登录」重试，不是 2912 次故障。
- 11-08 04:11 的 `Kernel-General` 注册表清理是 Windows 自动维护，出现在掉线**之后**，别误判成触发原因。
